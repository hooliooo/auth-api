Summary

The browser only ever holds an opaque, HttpOnly cookie. The backend for frontend (BFF) of RFC 10017 §6.1 runs as the two parts of the token handler pattern:

  • The OAuth proxy is a reverse proxy and the app's single origin. It answers every /api/* call with the session's access token instead of the cookie, and holds no credentials for the identity provider.
  • The OAuth agent behind it signs users in with an OpenID Connect provider (Keycloak here), proves its identity with signed assertions, keeps tokens in Redis encrypted under a key derived from the cookie, and refreshes them, also for the proxy through an internal endpoint.
  • What both use, from the session format to the CSRF check, metrics and shutdown, is one shared library, token-handler-common.

Motivation

  • The most exposed path held the most valuable secret. In the single BFF, the process that forwards every API call also held the client's Keycloak credentials and ran sign-in. Splitting it keeps the hot path free of anything that authenticates to Keycloak.
  • RFC 10017 names three jobs for the BFF: confidential client, session manager, request forwarder. The token handler pattern gives the first two to the OAuth agent and the third to the OAuth proxy, so each part has one reason to change.
  • They scale differently. The proxy carries every API call; the agent only sign-ins, logouts and one refresh per session every few minutes.
  • Shared vocabulary. Naming the parts, cookies, headers, keys and metrics after the pattern lets its documentation and anyone who knows it map straight onto the code.

Architecture

Who talks to whom, and what crosses each line. Nothing a script could steal ever reaches the browser; nothing on the hot path can pose as the client at Keycloak; and nothing the OAuth agent holds lets anyone pose as it without its private key.

Why a BFF at all

Tokens in browser storage can be read by any script on the page; an HttpOnly cookie cannot. Moving the OIDC client to the server turns "steal the token" into "use the session from the victim's own browser", which SameSite and the CSRF header then close off.

Why two parts

Every API call goes through the OAuth proxy, so it is the hot path and the most exposed part. It only reads sessions and never talks to Keycloak: when a token is about to expire it asks the OAuth agent's internal endpoint, which the Istio mesh opens only to the proxy's identity, over mutual TLS, and is never behind the ingress. Only the agent holds the client's credentials and refreshes, once per session across every instance. Together the two are RFC 10017's BFF: the agent its confidential client and session manager, the proxy its request forwarder.

Stateless instances

Everything a request needs lives in Redis: sessions, pending sign-ins, refresh locks, rate-limit counters, used logout-token ids. Any number of proxy and agent instances can serve the same user.

One public address, HTTPS only

Keycloak's issuer, https://keycloak-api/realms/test locally, is the same for browsers and pods: inside the cluster a DNS rewrite sends that name to the ingress. Keycloak URLs and the redirect URI must be https://; ALLOW_INSECURE_HTTP=true lifts that for local stacks only.

Signing in

The authorization-code flow with PKCE, step by step. The OAuth agent never sees the user's password: Keycloak does, on its own page.

What each value protects

  • state ties Keycloak's answer to the request that asked for it, and through the login cookie to this browser.
  • PKCE: the code is useless without the verifier, which never left the server.
  • nonce: the ID token was minted for this sign-in.
  • GETDEL: a pending sign-in completes exactly once.

Easy-to-miss details

  • Each sign-in gets its own login cookie, __Host-Http-login-<hash of state>, so two tabs signing in at once both complete.
  • The cookie check runs before GETDEL: a stranger opening someone else's callback URL is refused without consuming the pending sign-in.
  • A new session id on every sign-in; the browser's previous session is deleted (no fixation).
  • Return URLs are resolved against the app's own origin; only path, query and fragment survive.
  • With the rate-limit feature, sign-in starts are limited per client IP, since each writes to Redis without a session.

Scopes the OAuth agent controls

Every sign-in requests exactly OIDC_SCOPES (default openid). The browser cannot add any: a scope parameter on /auth/login is ignored, and an e2e test checks the URL Keycloak receives. Startup refuses a setting without openid or with offline_access, whose tokens would outlive the Keycloak session.

ID token checks

Signature, issuer, audience, expiry, iat and nbf in the oidc crate; then here: the token type as the provider marks it (Keycloak: typ is ID; standard ID tokens carry none), azp is this client when there are several audiences, and the nonce matches in constant time.

Requests and token refresh

What happens to every /api/* call. The OAuth proxy forwards it with the session's access token when that token is valid for another 60 seconds; otherwise it asks the OAuth agent's internal endpoint, which refreshes under a Redis lock. The API never sees an expired token.

Why the proxy never refreshes

Refreshing needs the client's credentials and, with rotating refresh tokens, exactly one refresh per session across every instance. Keeping both in the agent means the hot path holds nothing that authenticates to Keycloak, and the lock logic exists once.

What the proxy checks first

In order: the CSRF header (403), the session cookie and its session (401), a usable token or one from the agent (401, 502, 503), a configured API (503), and a path that stays under its base (400). A refusal is an empty response that still carries its request id.

Logging out

Two ways a session ends early: the user asks, or the provider tells the OAuth agent that the user's session there is over (signed out elsewhere, or by an admin). The diagram shows Keycloak; with any other provider the user logout differs as described below.

User logout

  • The OAuth agent session and its index entry are deleted first.
  • With Keycloak, POST to Keycloak's end-session endpoint with the refresh token and client authentication. This also revokes the refresh token and notifies the session's other clients.
  • logoutUrl is the app's start page. If Keycloak could not be told, it is Keycloak's own logout page with client_id and post_logout_redirect_uri, and no id_token_hint, so no token ever appears in a URL or history.
  • Cache-Control: no-store; the session cookie is cleared.
  • Other providers (IDENTITY_PROVIDER=oidc): the refresh token is revoked at the revocation endpoint (RFC 7009) with client authentication, and logoutUrl is always the provider's logout page, without a token, since the provider's own session can only end in the browser. A provider that publishes no revocation or logout endpoint skips that step, logged; without a logout page, logoutUrl is the start page.

Back-channel logout

  • Signature, issuer, audience, then the Back-Channel Logout §2.6 checks in oidc::logout::logout_claims: the logout event, no nonce, a sid or sub, a jti, and an iat no older than 120 s.
  • Each token works once: EXISTS on its jti, then delete the sessions, then mark the jti used. Marking it last means a failed delete can be retried by Keycloak with the same token.
  • Keycloak's client needs "Backchannel logout session required" on, or the token arrives without a sid.

Sign out everywhere

One browser has one Keycloak SSO session, however many apps it signed into. Ending it, from this OAuth agent or anywhere else, ends every OAuth agent session tied to it through back-channel logout.

Cookies

Each cookie holds one random 256-bit value and nothing else. The __Host-Http- prefix (RFC 6265bis, as RFC 10017 §6.1.3.2 asks) makes the browser require Secure, Path=/ and no Domain, so no subdomain can set or overwrite them, and accept them only from a Set-Cookie header, never from page JavaScript.

Reference-level explanation

How each part works, in enough detail to change it.

Client authentication

How the OAuth agent proves to Keycloak that it is the OAuth agent, on every token, refresh and logout call. private_key_jwt (RFC 7523) is the preferred method; a client secret still works as a fallback.

client_secretprivate_key_jwt

Setting it up

  • CLIENT_CREDENTIALS=private_key_jwt, CLIENT_KEY_FILE = an EC P-256 private key in PEM.
  • CLIENT_KEY_ID optional; default is the key's JWK thumbprint (RFC 7638).
  • Keycloak client: authenticator Signed JWT (client-jwt), algorithm ES256, Use JWKS URL on, JWKS URL http://oauth-agent:5100/.well-known/jwks.json. setup_realm.sh does this.

Local keys are never committed

Each developer runs crates/oauth-agent/dev/generate-client-key.sh once. It writes crates/oauth-agent/dev/client-key.pem, which git ignores. dev/k8s/up.sh runs it on first use and copies the key into the oauth-agent-client-key secret; after replacing the key, rerun dev/k8s/up.sh. Keycloak picks up the matching public key from the JWKS URL; nothing else changes. Production keys come from a secret store.

Rotating the key

1. Set CLIENT_NEXT_KEY_FILE (and optionally CLIENT_NEXT_KEY_ID) and restart: both public keys are published, the old one still signs. 2. Once Keycloak has the new key set, make it CLIENT_KEY_FILE and restart.

What Keycloak answers

A replayed assertion ("Token reuse detected"), an expired one ("Token is not active"), one signed with another key, and the old client secret all get 400 invalid_client, not 401. Three e2e tests send these straight to Keycloak.

How long a session lasts

With Keycloak, an OAuth agent session lasts exactly as long as the Keycloak session behind it, so the realm's SSO idle and maximum settings apply without being configured twice. Other providers do not report their session's lifetime, so there a session lasts an hour past its last sign-in or refresh.

Set by the provider

Each sign-in and each refresh stores the session for as long as the provider says its own session lasts (IdentityProvider::session_lifetime_secs). Keycloak says it in refresh_expires_in: the time until its session would idle out or hit its maximum. A standard provider says nothing, and Keycloak may say 0; then 1 hour.

Extended only by a refresh

Reading a session is a plain GET; it does not extend anything. Keycloak's session is extended only when a token is refreshed, so the OAuth agent does the same. An active user's access token expires every few minutes, so their session keeps moving; an idle one ends when Keycloak's does.

The OAuth agent's own cap

Whatever Keycloak allows, a session ends 24 hours after sign-in (SSO_MAX_SECS), checked on every load.

Ending early

Logout, a refresh Keycloak rejects (400 or 401), a new sign-in in the same browser, and back-channel logout all delete the session and its index entry.

What Redis holds

Key names use a SHA-256 hash of the secret they belong to, and session values are encrypted, so a copy of Redis lets nobody sign in or read a token. The agent writes everything; the proxy only reads sessions.

Encryption at rest

No key management at all: the encryption key is derived from the cookie value, which only the user's browser holds. The proxy opens sessions with the same code (token_handler_common::session::open) when the cookie arrives with an API call.

What a Redis leak exposes

Nothing usable. Without the cookies, neither the key names nor the values lead back to a session, and the ciphertext cannot be decrypted.

Tampering

Poly1305 authenticates every byte. Swapping values between keys, editing bytes or replaying a pending sign-in as a session all fail to open, and the agent and the proxy treat that as no session.

Derivation

HKDF-SHA256 with the fixed salt token-handler-sealed-v1 (built once, in a static SALT) and the purpose label as info; a fresh 12-byte nonce per write. Stored as nonce ‖ ciphertext ‖ tag.

The trade-off

The server cannot read a session without its cookie, so an admin "list sessions" view is impossible. Back-channel logout still works because it only deletes keys.

Refresh across instances and token rotation

The dev realm rotates refresh tokens and accepts each only once (revokeRefreshToken=true, refreshTokenMaxReuse=0). A second use of a spent token ends the user's Keycloak session, so only one instance may refresh a session at a time. Only OAuth agents refresh; OAuth proxies ask them.

No resurrected sessions

The refresh writes with SET … XX inside WRITE_IF_LOCK_HELD: only while the lock is still ours and the session still exists. A logout during a refresh stays a logout.

Each refresh keeps the rotated token

Every refresh stores the new refresh token Keycloak returned. An e2e test refreshes twice, checks a new refresh token was stored each time, then checks Keycloak refuses both spent tokens with 400.

Keycloak's same-second window

Keycloak only detects reuse when the token is older than the session's last refresh, compared in whole seconds. A spent token reused within the same second can slip through. The OAuth agent never reuses one; the test spaces its steps 1.1 s apart so it checks real behaviour.

Parallel requests

An e2e test fires five parallel requests with an expired token: all succeed and the session survives, which with single-use tokens is only possible if one refresh served them all.

Proxy headers

Which headers survive the trip through the OAuth proxy on an /api/* call. The browser's credentials stop at the proxy; the API sees only the bearer it attached and an address it determined. Everything else the proxy passes to the OAuth agent untouched, except the connection-only headers.

Path checks

The API URL is the path after /api appended to API_BASE_URL. Any . or .. segment is refused with 400, also when written as %2e or separated by \ or %5c, since lenient servers decode those. The final URL must still start with the base. With one configured API, this is how the proxy meets RFC 10017 §6.1.3.6's proxy restrictions.

Timeouts

One client for the API and the agent: 5 s to connect, at most 120 s of silence, no limit on total length, so long downloads and streams get through. It follows no redirects and decompresses nothing, so the agent's sign-in redirects and every body reach the browser as sent. Calls to the internal endpoint have a 15 s total limit.

The CSRF header

Every call the session cookie authorizes must carry x-csrf: 1, whatever its method (RFC 10017 §6.1.3.3.2): the proxy checks it on every /api/* call, the agent on its /auth/* routes except the ones a browser navigates to or Keycloak calls. Another site can only send a custom header after a CORS preflight, which is never granted.

The client's address

By default, the connection's address. Behind a reverse proxy, set CLIENT_IP_HEADER (e.g. cf-connecting-ip) and TRUSTED_PROXIES (the proxy's ranges): the header is believed only on connections from those ranges. A header without trusted proxies is a startup error. Both services read it the same way: the proxy for the API's X-Forwarded-For, the agent for its sign-in rate limit. An e2e test against an agent that trusts no proxy checks a forged header changes nothing.

Identity providers

The OAuth agent uses only standard OpenID Connect (discovery, authorization code with PKCE, refresh, private_key_jwt, back-channel logout) except in three places, which crates/oauth-agent/src/identity_provider.rs decides from IDENTITY_PROVIDER. The setting is required: a Keycloak deployment that silently fell back to the standard behaviour would lose Keycloak's token-type check and server-side logout, so the OAuth agent refuses to start without it.

Providers that publish less

The oidc crate no longer requires a discovery document to name an end-session or revocation endpoint (Microsoft Entra publishes no revocation endpoint, Google no end-session endpoint). Both are optional; the logout step that needs a missing one is skipped and logged.

Only the agent

Only the OAuth agent reads IDENTITY_PROVIDER: the OAuth proxy never talks to the provider, so it works the same with any of them.

Tested: the e2e cluster runs a second OAuth agent in standard mode, oauth-agent-oidc at https://auth-api-oidc, against the same Keycloak. A test signs in through it, logs out, and confirms Keycloak refuses the revoked refresh token. The tests register its addresses with the oauth-agent client on their first run.

Operating it

Build features (OAuth agent)

metricsonPrometheus on METRICS_ADDR

The agent's image builds with --build-arg FEATURES=metrics,rate-limit. Without a feature its code is compiled out; metrics::counter becomes a no-op, so callers need no cfg. The OAuth proxy has no features: it always serves metrics.

Metrics

  • token_handler_http_requests_total{route,method,status} and token_handler_http_request_duration_seconds by route template, so series stay bounded. The proxy counts /api/{*rest}; the agent counts its own routes.
  • Agent only: token_handler_sign_ins_total{outcome}, token_handler_token_refreshes_total{outcome} (refreshed, rejected, failed), token_handler_logouts_total{provider}, token_handler_backchannel_logouts_total{outcome}, token_handler_rate_limited_total.
  • Each service serves its own page on its own address, never the public port; the series names are the same, so dashboards need not know which process answered. An e2e test reads both.

Rate limit

Fixed window per client IP and minute, shared by all agent instances through Redis (INCR + EXPIRE NX). Default 10 sign-in starts per minute; over it, 429 with Retry-After. The agent sees the proxy's address, so it must trust the proxy's range for the client header; without that, everyone shares one address: rely on the ingress's limit and build without the feature.

Logs

  • Quiet by design: successful requests log nothing (the metrics count them). At info the log holds one configuration line per service at startup, failures, and events worth seeing: a session the provider ended, a sign-in the user did not finish, a dependency recovering.
  • Levels by cause: error for the service's own failures, with their causes; warn for the identity provider or a dependency misbehaving; info for routine events caused by users; debug for refused requests.
  • Outages once: Redis, the identity provider, the agent and the API each log one warning when they start failing and one line when they are back, with the failure count, instead of a line per request or probe.
  • One id across both services: the proxy gives every request an id (or keeps the caller's) and sends it to the agent, to the agent's internal endpoint and to the API; every line about the request carries it.
  • Format: LOG_FORMAT=json in the cluster, one object per line with the request's id, method and path; text by default, coloured only on a terminal. Panics are logged the same way.
  • Never logged: tokens, cookies, session ids, query strings, secrets.

Shutdown

Both services: Ctrl-C and SIGTERM let in-flight requests finish. Logging, shutdown, request ids and metrics are one shared implementation (token-handler-common).

Local cluster

dev/k8s/up.sh builds a kind cluster with Traefik (TLS from a local CA through cert-manager), Keycloak, Redis, the OAuth proxy at https://auth-api and the agent behind it, all in an Istio ambient mesh; --e2e adds the test helpers and two more agents. dev/k8s/down.sh deletes it. deploy/README.md has the details.

Technical implementation

What the branch changes, every file it consists of, and how to run it.

What changed

This round first; earlier rounds below it.

Token handler split (2026-11-14)

  • The BFF is split into the OAuth agent (crates/oauth-agent, was crates/bff) and the OAuth proxy (crates/oauth-proxy), a reverse proxy and the app's origin; what both use is in crates/token-handler-common.
  • The proxy answers /api/* and passes the rest to the agent; the agent no longer forwards API calls (no API_BASE_URL, no API client).
  • New: the agent's internal endpoint, POST /internal/access-token on port 5101, so only the agent refreshes and holds client credentials; first behind a shared secret, now behind the Istio mesh (see the end of this list).
  • Renamed on the wire: cookies __Host-Http-session and __Host-Http-login-*; CSRF header x-csrf, now required on reads too; Redis keys token-handler:*; metrics token_handler_*; sealing label token-handler-sealed-v1; Keycloak client oauth-agent. Existing sessions end, and the SPA must send the new header.
  • Cleanup after the split: the internal endpoint's path, headers and answer defined once, in the shared library; the agent uses the shared session checks (past_cap, usable_access_token) instead of its own copies; the shared library exposes only what the services call; one settings reader for both services; the agent imports the shared modules directly instead of through re-exports; the end-to-end helpers use the shared sealing and key formats, while the cookie and CSRF header names stay written out as the SPA's contract; unused dependencies removed; the compose stack is removed, so the cluster is the one local setup; dependency updates for three advisories. Then: one with_causes for both services, so the proxy's logs keep the cause of a failed call (an untrusted certificate, a refused connection) as the agent's do; the agent's metrics docs point to the shared list; the two test agents are built from the agent's own manifest with kustomize patches instead of a copy. Finally: the standalone Keycloak compose stack in iam-config (with its observability stack and image build scripts) is removed, and the realm setup allows sign-in only at agent_base_url; the tests register their other test agents themselves. Last: the internal endpoint moved from a shared secret over plain HTTP to the Istio mesh in ambient mode: ztunnel's mutual TLS between the pods' identities, and an AuthorizationPolicy admitting only the proxy's service account to port 5101; the agent serves the endpoint only with INTERNAL_ENDPOINT=mesh, and the application holds no secret or certificate for it.
  • Logging: JSON lines in the cluster at info; each dependency outage logged once when it starts and once when it ends; routine user events (a cancelled or stale sign-in, a session the provider ended) at info instead of warn; server errors with their causes; one request id across the proxy, the agent's internal endpoint and the API; a configuration line at startup; panics logged as events.
  • Since the last version of this guide, already on develop: the local kind cluster replaces the Docker stacks; one Keycloak address for browsers and pods (no DISCOVERY_URI); CLIENT_AUTH is now CLIENT_CREDENTIALS; the oidc crate is split into verifier, well_known, jwks and retry; the API's crates are outside this workspace.

Provider-neutral (2026-10-12)

  • IDENTITY_PROVIDER, required in the BFF and the API: keycloak keeps every behaviour above; oidc works with any OpenID Connect provider.
  • Provider-dependent ID token type check, session lifetime and logout (provider.rs); revocation-based logout for standard providers.
  • oidc crate: end-session and revocation endpoints optional in discovery.
  • API: a standard access-token reader beside Keycloak's, sharing the claim logic.
  • E2E: a standard-mode BFF and a logout test against it; the realm accepts its callback.

Sessions

  • Lifetime follows Keycloak's refresh_expires_in; only a refresh extends it (no sliding GETEX).
  • Per-state login cookies: parallel sign-ins in one browser work.
  • Back-channel logout: iat age and one use per jti.

Keycloak

  • private_key_jwt with a published JWKS and key rotation; dev keys generated locally, never committed.
  • Server-side end-session with the refresh token; logoutUrl is the start page.
  • Full scope off, minimal default scopes, API audience mapper, refresh-token rotation with no reuse.
  • Scopes fixed by OIDC_SCOPES.

Proxy and edge

  • Forwarding headers stripped, own X-Forwarded-For; trusted-proxy client IP.
  • Encoded dot segments refused.
  • Request ids; per-IP sign-in rate limit; Prometheus metrics on a separate port.
  • Configurable listen address; HTTPS enforced unless explicitly allowed.

oidc crate and tooling

  • Algorithm from the JWK, iat/nbf checks, HTTPS transport, endpoint rebasing fix, key-cache fast path.
  • aws_lc_rs backend: the rsa advisory is gone.
  • API requires typ: Bearer.
  • Pinned toolchain, cargo deny, documentation on every item, README, pipefail in the setup scripts.

Trying it locally

Bring up the cluster, with the test helpers, and run the end-to-end suite:

dev/k8s/up.sh --e2e
cargo test -p oauth-agent --features e2e --test e2e

Then sign in at https://auth-api/auth/login as alice (password test); https://auth-api/auth/session shows who is signed in. Each service's metrics are on 127.0.0.1:19100 (agent) and 127.0.0.1:19101 (proxy). dev/k8s/down.sh deletes the cluster.

Drawbacks

  • Two services instead of one, and a service mesh (Istio) for the call between them: two images, two deployments, and the mesh to install, upgrade and watch.
  • A refresh costs one more hop: the proxy calls the agent's internal endpoint, which then calls Keycloak. It happens once per session every few minutes, so it does not show in throughput.
  • Renaming the cookies, CSRF header and Redis keys ends every existing session, and the SPA must send x-csrf; dashboards need the token_handler_* metric names.
  • The proxy and the agent must agree on the session format; one shared library makes that a build-time guarantee, but both must be deployed from the same version.

Appendices

The decisions behind this RFC, and how it was verified.

A. Decision log

ADR-001: Split the BFF into an OAuth agent and an OAuth proxy

Accepted

Context

The process forwarding every API call also held the client's credentials and ran sign-in.

Decision

The token handler pattern: the agent is the confidential client and session manager; the proxy, a reverse proxy, is the origin and forwards API calls.

Consequences

Two services; the hot path holds no credentials; each part scales with its own load.

ADR-002: Only the agent refreshes

Accepted

Context

Refreshing needs client credentials and, with single-use refresh tokens, one refresh per session.

Decision

The proxy asks POST /internal/access-token on port 5101, never behind the ingress.

Consequences

One more hop per refresh; the lock logic exists once.

ADR-003: The proxy is axum, not Pingora

Accepted

Context

A Pingora prototype was about 10% faster than the BFF's forwarding; the session read dominates either way.

Decision

Write the proxy in axum, like the agent.

Consequences

One framework; the axum proxy measures level with the old forwarding; Pingora stays an option for edge cases.

ADR-004: One shared library for both services

Accepted

Context

Session format, cookies, CSRF, request ids, metrics, logging and shutdown were copied in both services.

Decision

token-handler-common holds them, including the axum middleware; what crosses to the API stays in the proxy.

Consequences

One copy of the security-sensitive rules; both services deploy from one version.

ADR-005: Names follow the token handler pattern, on the wire too

Accepted

Context

The crates, cookies, CSRF header, Redis keys, metrics and Keycloak client were named after the BFF.

Decision

oauth-agent, oauth-proxy, token-handler-common; __Host-Http-session, x-csrf, token-handler:*, token_handler_*, client oauth-agent.

Consequences

Existing sessions end; the SPA sends the new header; dashboards follow the new metric names.

ADR-006: The proxy keeps the name OAuth proxy

Accepted

Context

It is a reverse proxy; oauth-reverse-proxy was proposed.

Decision

Keep the pattern's name; the docs say it is a reverse proxy.

Consequences

Vocabulary matches the pattern; no forward proxy exists to confuse it with.

ADR-007: Sessions stay in Redis

Accepted

Context

RFC 10017 §6.1.2.3 recommends sessions in the cookie for large-scale deployments.

Decision

Keep server-side sessions, sealed in Redis.

Consequences

One Redis read per API call; refresh coordination and back-channel logout keep working.

ADR-008: The mesh secures the internal endpoint

Accepted

Context

A shared secret in a header over plain HTTP could be read off the pod network, replayed with any known session id, and never expired.

Decision

Istio in ambient mode: ztunnel gives the pods mutual TLS between their service-account identities, and the agent's AuthorizationPolicy admits only the proxy's to port 5101. The application holds no secret or certificate; the agent serves the endpoint only with INTERNAL_ENDPOINT=mesh.

Consequences

Encrypted, both sides authenticated, nothing to leak or replay; certificates issued and rotated by Istio; the mesh is a dependency, so a cluster without it gets no internal endpoint rather than an open one.
